### 🎨 바이브 코딩 (Vibe Coding)

> AI한테 시켜서 코드 만들기 = **"대화로 프로그래밍"**

**실제 대화 예시:**

```
나: "PDF 파일에서 텍스트 추출하는 기능 만들어줘"

Claude AI:
"알겠습니다. PyMuPDF 라이브러리를 사용하겠습니다.
[코드 작성 중...]
완료했습니다. pdf_extractor.py 파일을 확인해주세요."

나: "실행했는데 한글이 깨져요"

Claude AI:
"아, UTF-8 인코딩 문제네요. 수정하겠습니다.
[코드 수정...]
이제 한글도 정상적으로 출력됩니다."

나: "오! 됐다. 고마워 👍"
```

### 💡 핵심 메시지

- ❌ 코딩 언어 몰라도 됨
- ❌ 전공 지식 없어도 됨
- ✅ **한국어로 명확하게 설명만 하면 됨**
- ✅ **AI가 코드 작성 + 디버깅까지**

# PART 2: RAG란 무엇인가 (15분)

## 슬라이드 6: RAG를 3초만에 이해하기

### 🎯 초간단 정의

**RAG = 검색 + AI**

> "AI가 먼저 문서를 검색하고, 그 결과를 보고 답변하는 것"

### 📚 시험 비유로 이해하기

| 일반 ChatGPT | RAG 시스템 |
|-------------|-----------|
| 📖 시험볼 때 **머릿속으로만** 푸는 것 | 📚 시험볼 때 **책 펴놓고** 푸는 것 |
| 외운 것만 알고, 새로운 건 모름 | 모르면 책에서 찾아서 답변 |
| **한계**: 학습 데이터에만 의존 | **장점**: 최신 정보도 검색 가능 |
| **문제**: 우리 회사 문서 모름 ❌ | **해결**: 우리 문서 찾아보고 답함 ✅ |

### 💬 실제 차이

**일반 ChatGPT한테 물어보면:**
```
Q: "2024년 중계차 렌즈 오버홀 비용은?"
A: "죄송합니다. 저는 귀사의 내부 문서에 접근할 수 없어
    정확한 정보를 제공할 수 없습니다."
```

**AI-CHAT (RAG)한테 물어보면:**
```
Q: "2024년 중계차 렌즈 오버홀 비용은?"
A: "2024년 3월 15일 중계차 렌즈 오버홀 문서에 따르면,
    총 비용은 12,500,000원이었습니다.
    (근거: 2024-03-15_중계차_렌즈_오버홀.pdf)"
```

## 슬라이드 7: RAG 동작 원리 (더 쉽게)

### 🔍 네이버 검색과 비교

**네이버/구글 검색:**
```
1. 검색어 입력 → 2. 웹페이지 찾음 → 3. 링크 보여줌
```
→ **사용자가 직접 클릭해서 읽어야 함**

**RAG 시스템:**
```
1. 질문 입력 → 2. 문서 찾음 → 3. AI가 읽고 정리해서 답변
```
→ **AI가 읽고 요약해서 알려줌**

### 📊 비교표

| 구분 | 네이버/구글 | RAG |
|------|------------|-----|
| **결과** | 링크 리스트 | **답변** |
| **추가 작업** | 직접 클릭해서 읽어야 함 | 필요 없음 |
| **정보** | 어디 있는지 알려줌 | **뭐라고 써있는지** 알려줌 |
| **시간** | 5-10분 (읽는 시간) | **5초** |

> **핵심 차이**: "어디 있어?" vs "뭐라고 써있어?"

## 슬라이드 8: RAG의 3단계 작동 원리

### 1️⃣ 검색 (Retrieval)

```
사용자 질문: "렌즈 오버홀 비용은?"
        ↓
키워드 추출: [렌즈, 오버홀, 비용]
        ↓
문서 검색 (BM25): 관련도 점수 계산
        ↓
상위 5개 문서 선택
```

**검색 결과 예시:**
```
1. 2024-03-15_중계차_렌즈_오버홀.pdf (점수: 12.5)
2. 2024-08-10_카메라_렌즈_교체.pdf (점수: 8.3)
3. 2024-02-01_광학장비_점검.pdf (점수: 6.7)
```

### 2️⃣ 증강 (Augmentation)

검색된 문서 + 사용자 질문 → **하나의 프롬프트로 결합**

```
프롬프트:
"""
아래 문서를 참고하여 질문에 답변하세요.

[문서 1: 2024-03-15_중계차_렌즈_오버홀.pdf]
- 기안일자: 2024-03-10
- 기안자: 유인혁
- 총 비용: 12,500,000원
- 내용: 중계차 1호 카메라 렌즈 오버홀...

[문서 2: ...]

질문: 렌즈 오버홀 비용은 얼마였어?
"""
```

### 3️⃣ 생성 (Generation)

LLM이 프롬프트를 읽고 답변 생성

```
입력: 프롬프트 (문서 + 질문)
        ↓
Qwen2.5-72B 모델 (AI 두뇌)
        ↓
출력: "2024년 3월 15일 중계차 렌즈 오버홀 비용은
      12,500,000원이었습니다.
      (근거: 2024-03-15_중계차_렌즈_오버홀.pdf)"
```

## 슬라이드 9: RAG vs Fine-tuning - 왜 RAG를 선택했나?

### 📊 비교표

| 비교 항목 | RAG | Fine-tuning |
|----------|-----|-------------|
| **데이터 반영** | ⚡ 실시간 (문서 추가 즉시) | 🐢 재학습 필요 (수일~수주) |
| **투명성** | ✅ 높음 (출처 문서 제시) | ❌ 낮음 (블랙박스) |
| **비용** | 💰 낮음 (검색만) | 💸 높음 (GPU 학습 비용) |
| **정확도** | 📄 문서 기반 (환각↓) | 🎯 일반화 능력↑ |
| **업데이트** | 🔄 문서만 추가하면 끝 | 🔁 재학습 + 검증 필요 |
| **적합 사례** | 문서 Q&A, 고객 지원 | 도메인 특화 대화 |

### 🎯 AI-CHAT이 RAG를 선택한 3가지 이유

1. **문서가 자주 추가됨** (월 10-20개)
   - Fine-tuning: 매달 재학습? 불가능
   - RAG: 문서 추가하면 바로 검색 가능

2. **정확한 출처 제시 필요** (의사결정 근거)
   - Fine-tuning: "어디서 나온 정보지?" 알 수 없음
   - RAG: 문서 링크 + 페이지 번호 제공

3. **비용 효율적**
   - Fine-tuning: H100 GPU로 수일간 학습 (전기세 폭탄)
   - RAG: 검색만 하면 됨 (저렴!)

## 슬라이드 10: 용어 정리 - 이것만 알면 됨

### 🔤 필수 용어 (초보자용)

| 용어 | 쉽게 말하면 | 비유 |
|------|-----------|------|
| **LLM** | AI 두뇌 (ChatGPT 같은 것) | 사람의 뇌 |
| **7B, 72B** | 두뇌 크기 (숫자↑ = 똑똑↑) | 초등학생 vs 교수 |
| **토큰** | AI가 읽는 단위 | 한글 1자 ≈ 토큰 1개 |
| **벡터** | 문장을 숫자로 바꾼 것 | 좌표 (검색용) |
| **OCR** | 이미지에서 글자 읽기 | 스캔 문서→텍스트 |
| **프롬프트** | AI한테 하는 질문/명령 | AI와의 대화 |

### 🎓 심화 용어 (개발자용)

| 용어 | 정의 | AI-CHAT에서의 역할 |
|------|------|-------------------|
| **BM25** | 키워드 검색 알고리즘 | 문서 관련도 점수 계산 |
| **Embedding** | 텍스트→벡터 변환 | 의미 기반 검색 |
| **Context Window** | LLM이 한 번에 읽을 수 있는 길이 | Qwen: 32K 토큰 |
| **Temperature** | 생성 무작위성 (0=결정적) | 0.1 (일관성 중시) |
| **Quantization** | 모델 경량화 (16bit→4bit) | AWQ 양자화 (메모리 75%↓) |

### 🚫 몰라도 되는 것

**임베딩, 코사인 유사도, 트랜스포머, 어텐션, RNN, LSTM...**

→ **그냥 몰라도 됩니다!** AI한테 물어보면 됨.

## 슬라이드 11: 모델 크기가 중요한 이유

### 🧠 모델 크기 = 똑똑함의 척도

| 모델 크기 | 비유 | 답변 수준 | 예시 |
|---------|------|----------|------|
| **7B** (70억) | 초등학생 | "뭐라고요?" | "알려드릴 수 있나요?" |
| **13B** (130억) | 중학생 | "음... 아마도..." | "렌즈 관련 문서가 있는 것 같아요" |
| **72B** (720억) | 대학교수 | "정확히 말씀드리면..." | "2024년 3월 15일 중계차 렌즈..." |

### 💬 실제 답변 비교

**질문: "광화문 무선 마이크 교체 건 알려줘"**

**7B 모델 (작은 AI):**
```
알려드릴 수 있나요? 무선 마이크에 대한 정보가 필요하신가요?
```
→ 😞 **답변 실패** (질문만 되물음)

**72B 모델 (큰 AI):**
```
광화문 무선 마이크 교체 관련 문서입니다:

[문서 정보]
- 제목: 광화문 무선 마이크 노후화 및 단종으로 인한 장비 교체 건
- 날짜: 2025-07-04
- 카테고리: 음향
- 사유: 기존 장비 노후화 및 단종

출처: 2025-07-04_광화문_무선_마이크_노후화_및_단종으로_인한_장비_교체_건.pdf
```
→ 😊 **완벽한 답변** (제목 + 날짜 + 출처)

### 📈 성능 차이 (정량적)

| 항목 | 7B | 72B |
|------|-----|-----|
| 답변 정확도 | 60% | **95%** |
| 환각 발생률 | 15% | **2%** |
| 복잡한 질문 성공률 | 40% | **90%** |
| 출처 제시율 | 70% | **98%** |

## 슬라이드 12: 전체 시스템 구조


```python
def compress(results: list, ratio: float = 0.7):
    # 1. 상위 N개 선택
    n = int(len(results) * ratio)
    compressed = results[:n]

    # 2. 중복 제거
    compressed = remove_duplicates(compressed)
```

## 슬라이드 17: STEP 2 상세 - BM25 검색

### 📐 BM25 알고리즘

**수식**:
```
BM25(D, Q) = Σ IDF(qi) × (f(qi,D) × (k1+1)) / (f(qi,D) + k1 × (1-b+b×|D|/avgdl))

여기서:
- D: 문서
- Q: 쿼리
- qi: 쿼리의 i번째 단어
- f(qi, D): 문서 D에서 qi의 빈도
- |D|: 문서 D의 길이
- avgdl: 전체 문서 평균 길이
- k1: 1.2 (빈도 포화 파라미터)
- b: 0.75 (길이 정규화)
```

**실제 계산 예시**:

```python
query = "렌즈 오버홀 비용"
tokens = ["렌즈", "오버홀", "비용"]

for doc in all_documents:
    score = 0
    for token in tokens:
        # 1. 용어 빈도 (TF)
        tf = doc.count(token)

        # 2. 역문서 빈도 (IDF)
        df = count_docs_with_token(token)
        idf = log(N / df)

        # 3. BM25 점수
        score += idf * (tf * (k1+1)) / (tf + k1 * (1-b+b*len(doc)/avgdl))

    results.append((doc, score))

# 정렬 및 상위 K개 선택
results.sort(key=lambda x: x[1], reverse=True)
top_k = results[:15]
```

```python
# Temperature Sampling
def sample_token(logits, temperature=0.1):
    # 1. Temperature 적용
    logits = logits / temperature

    # 2. Softmax (확률 분포로 변환)
    probs = softmax(logits)

    # 3. Top-p Sampling (Nucleus Sampling)
    sorted_probs = sort(probs, descending=True)
    cumsum = 0
    cutoff = 0
    for i, p in enumerate(sorted_probs):
        cumsum += p
        if cumsum >= 0.9:  # top_p = 0.9
            cutoff = i
            break

    # 4. 샘플링
    next_token = random.choice(sorted_probs[:cutoff])
    return next_token
```

```
일부 PDF는 이미지 스캔본
→ pdfplumber로 텍스트 추출 실패
```

**해결 (다단계 폴백)**:
```python
def extract_text(pdf_path):
    # 1차 시도: pdfplumber
    text = pdfplumber_extract(pdf_path)

    if len(text) < 100:  # 텍스트 부족
        logger.info(f"Low text quality, switching to OCR")
```

### 🚧 Challenge 2: 한국어 토큰화

**문제**:
```
영어 토크나이저 (whitespace):
"렌즈를 교체했다" → ["렌즈를", "교체했다"]

문제점: 조사(를, 했다)가 분리 안 됨
→ 검색 정확도 ↓
```

**해결 (KiwiPy 도입)**:
```python
from kiwipiepy import Kiwi

kiwi = Kiwi()
tokens = kiwi.tokenize("렌즈를 교체했다")
# [("렌즈", "NNG"), ("를", "JKO"), ("교체", "NNG"), ("했", "VV+EP"), ("다", "EF")]

# 명사/동사만 추출
keywords = [t.form for t in tokens if t.tag.startswith(('N', 'V'))]
# ["렌즈", "교체"]
```

**결과**:
- 검색 정확도: 75% → 95% (20%↑)
- 한국어 특화 처리로 업무 용어 정확히 인식

**초기 방식 (하드코딩)**:

```python
if "얼마" in query or "비용" in query:
    mode = "COST"

    mode = "SUMMARY"

```

**문제점**:
- 복잡한 질문 처리 불가
  - "2024년 문서 다 알려줘" → SEARCH? YEAR_SUMMARY?
- 유지보수 어려움 (100줄 if-else)
- 신뢰도 측정 불가

**해결 (YAML 패턴 + 우선순위)**:
```yaml
# config/query_routing_patterns.yaml
priority_chain:
  - year_summary
  - cost_intent
  - search
  - qa

patterns:
  year_summary:
    confidence: 0.95
    rules:
      - pattern: "(?i)(\d{4}).*문서.*다"
        priority: 100

  cost_intent:
    confidence: 0.95
    rules:
      - pattern: "(?i)(비용|얼마).*\?"
        priority: 90

conflict_rules:
  - patterns: [year_summary, cost_intent]
    winner: cost_intent
    condition: "has_cost_keyword"
```

**결과**:
- 라우팅 정확도: 78% → 94% (16%↑)
- 유지보수성 향상 (YAML 수정만)
- 신뢰도 기반 조기 경고

# 발표 대본 (전체)

## 오프닝 (1분)

안녕하세요. 오늘 제가 개발한 AI-CHAT 시스템에 대해 발표하겠습니다.

부제가 "코딩 몰라도 AI로 만드는 지능형 문서 검색"인데요, 과장이 아니라 진짜입니다. 저도 개발자가 아니거든요.

오늘 발표를 듣고 나시면, RAG가 뭔지, 챗봇이 어떻게 작동하는지, AI 모델은 어떤 종류가 있는지, 전부 이해하실 수 있을 겁니다.

## Part 1: 도입 (10분)

다들 이런 경험 한 번쯤 있으시죠?

"중계차 렌즈 오버홀 문서 어딨더라?" 하고 폴더 뒤지고, 파일 하나씩 열어보고... 30분, 1시간 지나고... 담당자한테 물어보려는데 휴가중이고.

그래서 생각했습니다. "이거 AI한테 물어보면 바로 알려주면 안 되나?"

그래서 만들었습니다. 이제 "중계차 렌즈 오버홀 문서 찾아줘" 하면 5초 안에 답이 나옵니다. 1시간 반 걸리던 게 5초. 1,080배 빨라진 거죠.

"잠깐, 이거 개발자 아니면 못 만드는 거 아니에요?" 하실 수 있는데요. 저도 개발자 아닙니다. 코딩 1도 몰라요.

비밀은 "바이브 코딩"이라는 건데요, 쉽게 말하면 AI한테 시켜서 코드 만드는 겁니다.

*(실제 대화 예시 보여주며)*

이게 전부입니다. 한국어로 설명하면 AI가 코드 작성하고, 에러도 고쳐주고, 다 해줍니다.

## Part 2: RAG 설명 (15분)

RAG가 뭔지 진짜 쉽게 설명드릴게요.

**RAG는 "검색 + AI"입니다.**

시험 비유로 설명하면, 일반 ChatGPT는 외운 것만 알아요. 시험 볼 때 머릿속으로만 푸는 거죠.

RAG는 책 펴놓고 시험 보는 거예요. 그래서 우리 회사 문서를 찾아보고 답변할 수 있는 거죠.

네이버 검색이랑 뭐가 다르냐면요, 네이버는 "어디 있는지" 알려줘요. RAG는 "내용이 뭔지" 알려줘요.

*(3단계 작동 원리 설명)*

1단계 검색, 2단계 증강, 3단계 생성. 이 3단계만 기억하시면 됩니다.

왜 Fine-tuning 안 하고 RAG 했냐면요, 문서가 자주 추가되거든요. Fine-tuning은 매번 재학습해야 하는데, RAG는 문서만 추가하면 바로 검색 가능합니다.

## Part 3: 아키텍처 (10분)

이제 시스템 구조를 보겠습니다.

*(3-Tier 아키텍처 다이어그램 가리키며)*

맨 위가 사용자가 보는 웹 화면이고요, 중간이 비즈니스 로직, 밑이 데이터 저장소입니다.

핵심은 이 RAG 파이프라인인데요, 4단계로 구성되어 있습니다.

1. Query Router: 질문 유형 분류
2. Hybrid Retriever: 문서 검색
3. Context Compressor: 결과 압축

*(데이터 흐름 다이어그램)*

PDF 원본에서 시작해서, 텍스트 추출하고, 메타데이터 파싱하고, 검색 인덱스 만들고... 이런 흐름입니다.

## Part 4: 파이프라인 (15분)

실제 질문이 들어왔을 때 어떻게 처리되는지 보겠습니다.

"2024년 렌즈 오버홀 비용은?" 이 질문이 들어오면...

*(6단계 플로우차트 따라가며)*

1단계에서 COST 모드로 분류하고, 2단계에서 BM25로 검색하고, 3단계에서 상위 3개 선택하고...

BM25 알고리즘이 어떻게 작동하는지 보면요, 이 수식이 복잡해 보이지만, 쉽게 말하면 "키워드가 얼마나 많이, 얼마나 중요하게 나오는지" 계산하는 거예요.

*(LLM 생성 과정)*

Qwen 모델이 80개 레이어를 거쳐서 답변을 만듭니다. vLLM이라는 엔진이 이걸 10배 빠르게 만들어주고요.

성능을 보면, LLM 생성이 전체의 88%를 차지합니다. 여기가 병목이죠. 그래서 캐싱이 중요합니다.

## Part 5: 기술 스택 (15분)

이제 기술적인 부분 들어갑니다.

*(기술 스택 계층 다이어그램)*

Python으로 만들었고요, Streamlit으로 웹 화면, FastAPI로 백엔드, vLLM으로 AI 추론을 합니다.

개발 기간은 3개월 걸렸어요. 퇴근 후 1-2시간씩. 첫 주는 유튜브로 공부하고, 그 다음엔 Claude한테 물어보면서 만들었습니다.

*(어려움과 해결 과정)*

물론 어려움도 있었어요.

첫 번째, 스캔 문서는 텍스트 추출이 안 됐는데, OCR 적용해서 해결했고요.

두 번째, 한국어 토큰화가 안 되서 KiwiPy라는 형태소 분석기 썼습니다.

세 번째, GPU 메모리 부족 문제는 AWQ 양자화로 해결했어요. 메모리를 75% 줄였습니다.

*(최적화 성과)*

인덱스 크기를 96% 줄였고, 2-tier 캐싱으로 응답 시간을 10배 단축했습니다.
